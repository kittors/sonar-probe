# Sonar

卡片式 VPS 探针面板。除了常规的机器监控，重点做了两件多数探针不做的事：**流量归因**（哪个服务、哪个 IP 把带宽吃掉了）和**可回溯的实时封禁**。

视觉上参照 DeepSeek 官网的设计语言：近白冷调底、毛玻璃卡片、极细边框、克制的阴影和动效，主色只在关键处出现。亮色/深色双主题。所有图表、图标、下拉、日历都是自绘的，没有引图表库或 UI 库。

```
┌─ 概览页 ──────────────────────────────────────┐
│  汇总条：在线数 / 实时带宽 / 周期流量 / 封禁 / 成本 │
│  卡片网格：每台机器一张，CPU 趋势线 + 三项占用     │
│           + 实时收发 + 流量配额 + 到期提醒        │
│  事件流                                        │
└───────────────────────────────────────────────┘
              ↓ 点卡片进入
┌─ 详情页（分三个标签）────────────────────────────┐
│  常驻：实时快照 —— CPU / 内存 / 磁盘 / 负载 四个环 │
│  负载：四张曲线图，可切 15 分钟 ~ 24 小时         │
│  流量：日流量柱状图 + 按进程/服务的归因排行        │
│  安全：对端 IP 排行（含威胁评分）+ 封禁规则        │
│  后两个标签共用一个日期范围，默认落在当前计费周期  │
└───────────────────────────────────────────────┘
```

## 它和 nezha 之类探针的区别

| | 常见探针 | Sonar |
|---|---|---|
| 流量 | 只有总量 | 拆到进程/服务，再拆到对端 IP，任意时间范围可查 |
| 流量周期 | 固定自然月 | 可按开通日重置，支持人工校准补齐装探针前的用量 |
| 异常来源 | 看不到 | 威胁评分 + 可解释的判定依据 |
| 处置 | 自己 ssh 上去敲 iptables | 面板里点，带预检和二次确认 |
| 封禁有效期 | 手动清理 | 交给 nftables set timeout，内核自动解封 |
| 权限 | 全有或全无 | 23 个能力点 + 可自定义角色，按钮级控制，带提权防护与审计 |
| 登录 | 单一方式 | 密码 / GitHub 可并存于同一账号，权限改动实时推送 |
| SSH | 自己记 IP 和端口 | 公钥分发 + 别名目录 + **机器上密钥的实况对账** |
| 成本 | 各币种面值直接相加 | 按汇率折算成一种货币，附换算前明细 |
| 流量口径 | 写死 1024 进制、双向计费 | 进制和计费方向可配，对齐服务商账单 |

## 安装

两个脚本，都是幂等的，重复执行只更新产物不动数据。

### 面板

```bash
sudo ./scripts/install-panel.sh --from-source . --domain sonar.example.com
```

它会装好 Node 运行时（用官方 tarball，不污染系统包）、建专用系统用户、写好带沙箱的 systemd 单元、生成 agent token，顺带配 nginx 反代和 Let's Encrypt 证书。

不想要 nginx 就去掉 `--domain`，面板只监听 `127.0.0.1:8787`，自己接反代。

装完的配置在 `/opt/sonar/server/data/panel.env`，里面有生成好的 `SONAR_AGENT_TOKEN`。

### 采集端

在每台要监控的机器上：

```bash
sudo ./scripts/install-agent.sh \
  --panel https://sonar.example.com \
  --token <面板生成的 token> \
  --id hkg-edge-01 \
  --name "香港 · 边缘节点"
```

装之前可以先探路，这一步不装任何东西也不改任何配置：

```bash
sudo ./scripts/install-agent.sh --check-only
```

它会告诉你这台机器能采到什么。**特别是流量归因能不能用** —— 这一项在很多机器上是采不到的，而且失败得很安静：CPU、内存、网络一切正常，唯独「对端 IP 流量」永远是空的。原因见下一节。

默认封禁是只读的：面板下发的 enforce 指令只会打印不会真改防火墙。确认流程没问题后加 `--enforce` 重跑即可放开。

### 从源码跑

```bash
pnpm install
```

```bash
pnpm dev
```

面板 http://localhost:5273 ，接口在 8787。

开发时想要一屏有数据的图，可以打开内置模拟器：

```bash
SONAR_SIMULATOR=1 pnpm dev:server
```

它会生成 12 台虚构机器并回填 30 天流量和 24 小时曲线。**默认是关的** —— 不显式打开就不会有任何虚构数据，免得真机和假机混在一起。

## 流量归因是怎么做到的

Linux 没有"每进程用了多少流量"的现成接口，Sonar 靠三张表拼出来：

| 数据源 | 提供什么 |
|---|---|
| `/proc/net/nf_conntrack` | 每条连接的双向字节数 |
| `/proc/net/{tcp,udp}*` | 本地端口 → socket inode |
| `/proc/<pid>/fd/*` | socket inode → 进程 |

顺着这条链把 conntrack 里的本地端口找到进程，就得到进程级流量；按对端地址聚合，就得到 IP 级流量。两者是同一份数据的两个视角。

### 为什么要做流级差分

conntrack 给的 `bytes` 是**连接建立以来**的累计值，而且连接关闭后条目会过期消失。把这份快照原样当成流量上报，得到的数字和时间没有关系：

- 一条挂了三天的长连接，那 60 GB 会在每一拍里被重复报一遍；
- 一条刚结束的短连接，它的字节数下一拍就彻底不见了。

0.1.0 就是这么做的，面板还按天覆盖写 —— 于是「近 7 天谁吃了流量」实际回答的是「昨晚最后一秒谁连着」。一台生产机上实测：近 7 天归因合计 11.03 GB，同期真实走了 278.45 GB，**覆盖率 4%**。

现在采集端记住每条连接上一拍的累计值，只上报两拍之间的**增量**；面板累加而不是覆盖。增量是可加的，跨天求和才有意义。三个配套的点：

- **首次采样只建基线。** 不然 agent 每次重启都会把 conntrack 里那些已经跑了几小时的连接当成"这一拍新增的"，凭空多出一大笔。
- **上报失败不丢增量。** 增量是一次性的，这一拍没送到就再也补不回来，所以攒着，直到面板确认收下。
- **四元组被复用时全量计入。** 计数器往回走说明这是另一条连接了，记 0 会把它走过的量整个吞掉。

归因永远不会等于总量：没开 accounting 的那段时间、conntrack 表满被丢弃的条目、非 IP 流量，都落不进任何进程名下。所以卡片上直接写着「已归因 X / 总量 Y · Z%」—— 上一版之所以错了很久，正是因为界面上没有任何地方透露过这个差额。

> **面板升到 0.2.0 后，采集端也要一起升。** 上报里带一个 `attributionDelta` 标记，声明"我报的是增量"；面板只累加带这个标记的数据。0.1.0 的 agent 报的是快照，被累加的话两秒一次、一天四万多拍，排行榜上会长出几十 TB —— 所以它们的归因数据一律丢弃，并在事件流里说明要升级。基础指标（CPU、内存、流量总量）不受影响，老 agent 照常工作。

### 前置条件（很容易缺）

**一、conntrack 要开字节计数。**

```bash
sysctl -w net.netfilter.nf_conntrack_acct=1
```

不开的话 conntrack 里每条连接的 `bytes` 恒为 0。

**二、conntrack 得真的在跟踪连接。**

这一条最反直觉：**模块加载了不等于在工作**。conntrack 是按需启用的 —— 必须有 netfilter 规则引用它，内核才会开始记账。一台没装任何防火墙规则的干净云主机上，`lsmod` 能看到 `nf_conntrack`，但 `/proc/net/nf_conntrack` 永远是空的。

怎么判断：

```bash
awk '/^nf_conntrack /{print "引用计数:", $3}' /proc/modules
```

引用计数为 0 就说明没有任何规则在用它，表不会有数据。

给内核一个开始跟踪的理由，最轻量的做法是加一条只计数、不拦截、不改变转发行为的规则：

```bash
nft add table inet sonar_ct
nft add chain inet sonar_ct prerouting '{ type filter hook prerouting priority -300; policy accept; }'
nft add rule inet sonar_ct prerouting ct state new counter
```

这是防火墙改动，安装脚本**不会**替你执行。动手前确认你有带外访问（VNC / 救援控制台）。

**三、采集端需要 root**，否则读不了其他进程的 `/proc/<pid>/fd`。

任一条件不满足时归因返回空，但不影响 CPU、内存、磁盘、网络这些基础指标。

## 流量周期与校准

很多 VPS 的流量额度不是按自然月重置，而是从开通日算。面板支持给每台机器单独设账单日（每月 1–31 号，月末会自动夹取 —— 设 31 号时 2 月落在 28/29 号）。

另一个现实问题：探针总是中途才装的，装之前那段流量库里根本没有记录，面板的「已用」会一直比服务商账单小一截。所以有一个校准入口：填服务商后台此刻显示的真实值，系统存下**差额**而不是绝对值，后续增长照常实时累加，进入新周期后差额自动作废。

### 按时间范围看

详情页的流量和安全两个标签共用一个日期范围，默认落在**当前计费周期**（快捷项还有近 7 / 14 / 30 / 90 天，以及自绘的双月日历选任意区间）。共用一个区间是有意的：「这段时间走了 338 GB，其中 nginx 吃掉 210 GB」这句话要成立，两个数字就必须来自同一段时间，各查各的只会让人对着两个口径找原因。

## 通用设置

管理后台 →「通用设置」。收的是那些**同一份数据、换个人看就该换个口径**的东西。判断标准只有一条：它原本是代码里的字面量，而不同的人需要不同的值。

**成本与货币。** 每台机器各自记价格和币种，汇总时按汇率折算成一种展示货币 —— 之前是把各国货币的面值直接相加再统一标美元符号，12.9 美元 + 52 欧元 + 180 人民币会得出「$244.90」，而真实支出约合 94 美元。那个数字没有单位。汇率每天从公开接口自动拉一次（请求不带任何参数，内网部署可以关掉），也可以按币种手填覆盖 —— 信用卡入账汇率和实时中间价本来就有出入，认真对账时以账单上的为准。汇率若只能落到内置参考值，界面会明说，不装作是实时的。已过期的机器默认不计入。

**流量口径。** 两项，都直接影响配额告警准不准：

- **进制**（默认 1000）：服务商标称的「2 TB 流量」通常指 2×10¹² 字节，按 1024 进制会显示成 1.82 TB —— 一台机器永远到不了面板上的「2 TB」，用到 1.82 就已经满额了。默认从 1024 改成 1000，是因为 1024 配上默认关闭的「单位写法」会把 GiB 印成「GB」：面板写 315 GB、服务商后台写 328.26 GB，两个数字单位不同却长得一模一样，人只会得出「探针算错了」的结论（那两个数字背后其实是同一个 338,579,939,704 字节）。显式保存过这一项的部署不受影响。
- **计费方向**：很多机房只计出站。按双向算，一台正常同步镜像的机器会显示成随时要超额。

> 从 0.1.0 升上来且从没动过设置的面板，所有流量数字会变大约 7%（**数据没变，只是换了进制**），已填的配额需要按账单口径重填一次 —— 之前填「2 TB」存进去的是 2 TiB = 2199 GB，而服务商给的是 2000 GB。

**时区。** 决定流量按哪一天归档、周期从哪天切。原先一律按 UTC：UTC+8 的人在晚上 8 点才看到「今日流量」归零，而服务商后台早在 8 小时前就翻了页。这一项只管业务时间，界面上的「11 小时前」仍按你自己电脑的时区显示。改时区不重算历史，换的那天会有几小时偏差。

**状态与告警。** 离线判定秒数、CPU/内存/磁盘告警线、负载倍数、到期提醒天数、配额提醒百分比。没有一组阈值对所有机器都合适 —— 一台构建机负载常年在核心数的三四倍是它的正常状态，按 2.5 倍判会让它永远挂着告警，于是所有人都学会了无视那个颜色。

**数据保留。** 高频指标保留小时数、审计日志保留天数、流量归因明细保留天数（后两项 0 为永久）。审计表原先只写不清，每次浏览落一行，常看的面板一年能攒几十万条；归因改成累加之后同样只增不减，每机每天最多 60 个服务 + 200 个对端。**日流量总账不在清理范围内** —— 它每机每天只有一行，却是唯一能回答「去年这个月用了多少」的账本。

改动会通过 WebSocket 推给所有在线的人。口径是全局的：一个人把进制从 1024 改成 1000，另一个正开着页面的人如果还按旧口径渲染，两人对着同一台机器会读出差 10% 的数字，而谁都不知道对方看到的是什么。

## SSH 接入

面板做两件事：**分发公钥**和**维护连接目录**。它不做会话代理 —— 不存私钥、不建隧道、没有 Web 终端。你的 ssh 连接直连目标机器，一个字节都不经过面板，所以面板挂了不影响任何人登录。

这一点是和哪吒那类探针最根本的差别。它们的 WebSSH 是 agent 建反向隧道再执行面板下发的命令，等于在每台机器上开了个受控后门——搜索引擎里"哪吒 SSH 关闭"是个高频词条。Sonar 选择不提供那个能力，代价是不能在浏览器里敲命令，换来的是**面板被攻破也拿不到任何一台机器**。

### 它比连接管理器多知道什么

Termius、Tabby、assh 装在你本机，只记得住"你打算怎么连"。Sonar 的 agent 就跑在目标机器上，能回答"这台机器上现在到底有哪些钥匙"：

```
香港节点
  1 把公钥 · 0 把由 Sonar 管理
  root · ssh-rsa
  SHA256:strangerkey123                              来历不明
  装机时留下的
```

**这一格是整套东西最有价值的输出。** 一台买了两年、装过各种一键脚本的 VPS，它的 authorized_keys 里往往有几把谁也说不清来历的钥匙，而今天没有任何工具会告诉你这件事。

同一个道理还带来一个副产品：agent 能读到 `/etc/ssh/ssh_host_*_key.pub`，于是面板可以连 `known_hosts` 一起生成给你。首次连接时那句 `Are you sure you want to continue connecting?` 就不用盲按了——**TOFU 这个 SSH 最大的信任缺口，被机器里的眼线补上了**。装在你本机的客户端做不到这一点。

### 授权靠一条能读懂的命令

选一把钥匙和一台机器，面板生成这个：

```bash
u=root; h=$(getent passwd "$u" | cut -d: -f6) || { echo "用户 $u 不存在"; exit 1; }
install -d -m 700 -o "$u" -g "$(id -gn "$u")" "$h/.ssh"
touch "$h/.ssh/authorized_keys" && chown "$u" "$h/.ssh/authorized_keys" && chmod 600 "$h/.ssh/authorized_keys"
grep -qF 'AAAAC3Nza...' "$h/.ssh/authorized_keys" \
  || echo 'ssh-ed25519 AAAAC3Nza... sonar:alice:hkg-edge-01:20260825' >> "$h/.ssh/authorized_keys"
```

刻意生成**原生 shell 而不是 `curl | bash`**。装 agent 用 `curl|bash` 是合理的（那是装软件），但这条命令改的是这台机器的信任根——让人执行一个看不懂的脚本去改自己的信任根，本身就是讽刺。

每一行都在解决一种具体的翻车方式：

| 片段 | 防的是什么 |
|---|---|
| `install -d -m 700` | 目录权限不对时 sshd **静默拒绝**整个文件，这是 authorized_keys 失效的头号原因 |
| `chmod 600` | 同上，文件权限 |
| `grep -qF … \|\|` | 幂等。重复执行不会追加出十行一样的钥匙 |
| `>>` 而非 `>` | 绝不覆盖别人已有的钥匙 |
| `sonar:` 前缀 | 对账与安全删除的锚点，见下 |

### 只管自己装的

写进去的每一行 comment 都带 `sonar:所有者:机器:日期`。删除时**同时**要求指纹匹配和这个前缀——同一把公钥可能既被 Sonar 装过、又被人手工加过，只按指纹删会把手工那份也抹掉，那不是我们装的，无权处置。

### 撤销比授权危险一个数量级

新增一把钥匙最坏是多了个入口，删错一把的后果是**再也进不来**，而且没有任何界面能撤销。所以撤销的预检严得多：

| 硬拦 | 理由 |
|---|---|
| 还没采集到实况 | 所有判断都建立在实况上，没有它就是盲操作 |
| 实况超过 10 分钟 | **过期的实况比没有实况更危险**，因为人会以为它是准的 |
| 这是最后一把钥匙，且密码登录已关 | 删完就没有任何方式能登进去 |
| 是最后一把，但密码登录状态未知 | 按最坏情况处理 |

**agent 侧还会独立再判一次。** 面板预检过的事，agent 拿到指令后用它此刻看到的真相重新判断一遍——面板那份实况可能已经过时，也可能面板本身被攻破了。两边任一认为危险就不执行。

### 有效期由 sshd 和 agent 双重保证

OpenSSH 7.7（2018）给 authorized_keys 加了 `expiry-time` 选项，到点 sshd 自己拒绝这把钥匙。这和封禁把 TTL 交给 nftables 内核是同一个思路：**面板挂了也照常失效**。

但低于 7.7 的 sshd 会把带这个选项的**整行**当成坏选项拒绝——那把钥匙直接失效，表现是"授权成功但连不上"。所以面板会先看 agent 上报的版本，低于 7.7 时硬拦住带有效期的授权，并提示改走 agent 下发（由 agent 本地定时清理来保证）。

agent 的清理不依赖面板：网断了、面板没了、agent 永久失联，临时授权照样按时消失。

### 远程下发是可选的，默认关闭

面板可以只生成命令，由你自己去机器上执行——那样面板永远不具备改动机器的能力。

要让 agent 直接改 authorized_keys，需要三件事同时成立：

1. agent 以 `-ssh-keys` 启动（**默认关闭**，和 `-enforce` 对封禁的关系一致）
2. 操作者有 `ssh:remote_apply` 能力
3. 这台机器完成了**每机独立密钥**升级（见下）

agent 收到的是结构化参数，不是命令字符串。面板给的那些命令文本只用于展示和存档，agent 一个字都不看——这里连 `exec` 都不需要，纯 Go 文件 IO。写入走"临时文件 → fsync → rename"的原子替换：直接改原文件时一次 OOM 或断电就会留下被截断的 authorized_keys，所有钥匙一起丢，机器立刻失联。

### 每机独立密钥

`SONAR_AGENT_TOKEN` 是全机队共享的，任何一台机器的 systemd unit 里都读得到。在"只上报数据"的年代这不算致命，但通道能反向下发密钥变更之后，同一个 token 让任何一台被攻破的机器可以：

- 拉取**任意**机器的待办指令，看到面板打算给谁装什么钥匙
- 替**任意**机器发回执，让面板显示一个虚假的"已撤销"

第二条尤其恶劣：它比没有这个功能更糟，因为人会依据那个假状态做安全决策。

所以 agent 注册时面板会换发一把只属于这台机器的密钥，落盘 `/var/lib/sonar/agent.secret`（0600）。**没有密钥的 agent 照常上报，只是收不到指令**——这道闸门让升级是自愿、可观测、可回滚的。

### 状态只由实况决定

一条授权只有在**机器实况里看到了**才会变成"生效中"。命令生成了不算，agent 回执说成功了也不算——那些只说明"我们试过了"。

反过来，一条生效中的授权在实况里消失，标成「已漂移」而不是「已撤销」：后者意味着"我们撤的"，而事实是有人手工删了，两者不能混为一谈。

### 不做的事

**不做 SSH CA / 短期证书。** 这是业界的终局方案（Teleport、Netflix BLESS、smallstep、Vault SSH 都用它），撤销一个人只需停止签发。但它的主要卖点——"人走了不用跑遍每台机器删钥匙"——在有了远程下发之后已经由一键批量撤销覆盖了；而代价是 CA 私钥保管、签发服务、客户端要拿证书再连。数据模型里授权已经是独立实体，将来加 CA 只是多一种 `method`，不用重构。

**不碰 sshd_config，不重启 sshd。** authorized_keys 是即时生效、无需重启的，这正是它可以被安全操作的原因。改配置再重启是另一个量级：写错一个字母，sshd 起不来，没有救援控制台这台机器就废了。这条约束顺带排除了 EC2 Instance Connect 那套（要配 `AuthorizedKeysCommand`）和 GCP OS Login 那套（要改配置 + 重启 + 改 PAM 和 NSS）。

**面板只存指纹。** 从机器上扫回来的实况只保留 `SHA256:xxx`。公钥本身不是秘密，但"哪些公钥能进哪些机器"的完整地图对定向攻击极有价值——面板被拖库时，指纹够做对账，却复原不出可用的钥匙。

## 封禁

这是整个项目风险最高的功能，所以做了几层限制。

**默认只生成不执行。** 面板里点封禁，默认产出的是 dry-run 规则：命令写进数据库存档，不下发。要真正生效，需要在对话框里勾选 enforce，再勾一次确认框，服务端还要求请求体里带 `confirm` 字段等于目标 IP。

**预检拦截自伤操作。** 下面这些一律拒绝，并且把理由显示出来：

- 环回、RFC1918 私有网段、链路本地（含云厂商元数据地址 `169.254.169.254`）、CGNAT
- 目标机器自己的 IP
- 你当前的出口 IP（封了自己就连不上了）
- 面板地址（封了 agent 立刻失联）
- 比 `/24` 更宽的网段（IPv6 是 `/48`）

**目标地址必须是合法 IP 或 CIDR。** 用 `node:net` 做严格校验，`::1; whoami` 这类带 shell 元字符的输入在预检阶段就被拒掉，不会进入命令文本。

**agent 不执行面板发来的命令字符串。** 面板下发的 `commands` 只用于展示和审计，agent 拿到 target 和 ttl 后自己重新构造 `exec.Command("nft", args...)` 的参数数组，不经过 shell。面板一旦被攻破，也没法借下发命令在机器上执行任意代码。agent 还会独立再跑一遍守卫检查 —— 两边任一认为危险就不执行。

**agent 侧还有一道开关。** 不加 `-enforce` 启动时，收到 enforce 指令也只打印不执行。

**有效期由内核管。** 规则写进 nftables 的 set 并带 `timeout`，到点内核自动解封。面板挂了、网络断了、agent 崩了，都不影响解封 —— 不会出现"面板没了机器被永久锁死"。

## 登录与权限

### 三种登录方式

**用户名密码**、**GitHub OAuth**、**访客**。前两种可以指向同一个账号 —— 一个人既能用密码进来，也能绑着 GitHub，用哪条路进来都是同一个身份、同一份权限、同一条审计线索。

密码登录排在最前面，因为它是唯一不依赖外部配置的那条路。OAuth 没配好、GitHub 挂了、机器出不了网时，它是进门的兜底。

面板第一次启动会自动创建一个超级管理员，随机密码打印到日志并写进 `data/initial-admin.txt`（0600）：

```
┌─ 已创建初始管理员账号 ─────────────────────
│  用户名：admin
│  密码：  i94C9qFqyLL3QLjv75rE
└────────────────────────────────────────────
```

自动化部署可以用 `SONAR_ROOT_USER` / `SONAR_ROOT_PASSWORD` 指定。这两个变量**只在冷启动那一次读**，不做"每次启动都重置成环境变量里那个"—— 那等于在环境里长期放一把万能钥匙。

初始密码换掉之前，这个账号的权限被降到**和未登录访客一样**。不是弹一句提醒就放行：初始密码要么写在服务器的文件里，要么经过了管理员的口头转告，两种情况下都不止一个人知道它。降级而不是全封，是为了让人还能打开公开的概览页，而不是卡在一个哪儿都去不了的状态。

超级管理员不可降权、不可停用、不可删除。这条挡在数据层而不只是接口层 —— 改角色、停用、删除、批量导入每条路径都会经过同一处校验，日后多一个入口不会多一个缺口。

### 角色可配置

角色不再是代码里的常量表，而是数据库里的一张表，运行期可以随便增删改，带能力矩阵编辑器。改一个角色的能力集会**立刻推给所有在线的人**，不需要谁重新登录 —— 权限是服务端说了算的东西，它变了就该由服务端来通知。

但**能力点仍然写死在代码里**。分界线是这个：能力点一一对应路由上的 `requireCap`，凭空造一个 `node:destroy` 存进库，没有任何代码会读它，那不是一项权限，只是一行让人误以为生效了的配置。新增能力点必然伴随新增代码，所以它属于代码。

内置五个角色：管理员、运维、观察者、访客、未登录。都不能删（管理员没了没人管得住面板，未登录没了公开状态页渲染不出来），但除管理员外都能改能力集。管理员的能力集恒等于代码里定义的全部 —— 允许编辑的话，把 `user:manage` 摘掉之后就没有任何人能把它加回来，而新版本新增的能力点，管理员反而会是唯一没有的人。

「未登录」这个角色决定公开状态页显示到哪一层。它不挂在任何账号上，所以用户数显示为「—」而不是 0 —— 显示 0 会让人以为没人用、可以删，而它恰恰是影响面最大的一个。

### 提权防护

23 个能力点，粒度是按钮级。没有权限的东西**不渲染**，而不是渲染出来再禁用 —— 让人看见一个点不动的按钮只会制造困惑。敏感数据（完整 IP）在服务端就遮蔽掉了，前端打码不算数。

默认情况下，**谁都不能创建或授予自己没有的能力**。不堵的话，一个只有"建号"权限的人可以建一个管理员账号再登进去，一步就把"能开号"变成"能干任何事"。这条守卫覆盖三个入口：建号、改权限、重置密码 —— 重置别人的密码等于取得他的账号，漏掉它，前两条就都白堵了。

但一刀切会挡住一类正当需求：专职开账号的人需要给别人配置他自己用不上的权限，总不能为了给运维开号，先把自己变成运维。所以照 Kubernetes RBAC 的 `escalate` 动词做了一个显式出口 —— `user:escalate`，默认不给，标签直说"等同于可自我提权"。

被拦住时给的是人话，不是能力点的内部标识：

```
张三 拥有你没有的能力（进入机器详情页、查看未打码的 IP 地址 等 16 项），
不能修改他的权限。确实需要这么做的话，请管理员授予「授予自己没有的权限」。
```

设置分两级：`settings:view` 给到观察者以上（要按面板上的数字做判断，就得知道这些数字按什么口径算出来的），`settings:manage` 只给管理员并标成高危 —— 改流量口径会让所有人的配额百分比一起变，改保留天数会真的删掉数据。展示口径本身（进制、货币、时区）通过 `/api/settings/public` 对所有人开放，包括匿名访客：概览页是公开状态页，拿不到口径就没法正确渲染上面的数字。

### 账号维护

个人设置页可以改密码、绑定/解绑 GitHub。这一页不需要任何能力点 —— 挂在 `user:manage` 之类的能力下面，会导致一个被收走全部权限的人连密码都改不了，而那恰恰是最该让他改密码的处境。

**唯一的登录方式不能解绑。** 解开之后账号还在、权限还在、数据还在，但没有任何一条路能再登进去，而且没有任何界面能撤销它。和封禁那边"不许封掉自己的出口 IP"是同一类保护。

改密码会踢掉该账号在其它设备上的全部会话，但留着当前这个窗口。管理员重置他人密码则踢掉全部，并强制对方下次登录修改；新密码只在那一次响应里回显，服务端只存哈希，不留明文也不写日志。

删除账号会连带删掉他的登录方式，但**审计日志保留** —— 否则删号就成了洗白操作记录的手段。

管理后台能看到谁在线、谁看过什么、以及完整的操作审计日志。

## 安全

除了封禁那一节，还做了这些：

- **CSP、X-Frame-Options、nosniff、Referrer-Policy** 由应用层下发，换反代或自部署都不会丢
- **CORS 默认只放同源**，跨域来源要显式配 `SONAR_CORS_ORIGINS`
- **限流**：访客登录每 IP 十分钟 5 次，agent 上报每分钟 60 次
- **恒定时间比较** agent token 和会话凭据
- 会话是 httpOnly + SameSite=lax cookie；退出登录会清掉前端的机器列表缓存
- 用户填的外链（服务商控制台）前后端各校验一次协议，只放行 http/https

跑安全回归测试：

```bash
cd apps/server && pnpm test
```

## 威胁评分

评分不是黑盒。每一分都来自可解释的信号，面板会把判定依据原样列出来，让人在点封禁之前知道自己在封什么：

- 每连接字节数过低（高连接 + 低流量 = 典型爆破/扫描）
- 连接数绝对值过高
- 命中远程登录或数据库端口（22 / 3389 / 5900 / 3306 / 6379 / 27017）
- 已知威胁情报标记
